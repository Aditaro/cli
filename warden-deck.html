The problem

A failed migration reverts the data
and forgets the reason.

Migrations fail in production constantly. The standard response is a blind revert: the schema goes back, and every trace of why the change was attempted disappears with it.

The engineer picking up the incident reconstructs intent from a diff and a commit message — at the worst possible moment, under time pressure.

Git shows what changed. It doesn't show what you were trying to achieve.

Warden's user: anyone shipping schema or data migrations who wants recovery that explains itself.

How it works · one command

Checkpoint → impact → apply → validate → heal → explain

01 · Read intent

Entire checkpoint

Pull the recorded intent for this change via entire checkpoint explain — before anything touches the warehouse.

02 · Blast radius

Entire Graph impact

Run impact analysis on the affected symbol first, so the risk is known before it's taken.

03 · Apply

Delta migration

Record the pre-migration Delta version, then execute.

04 · Validate

Fail fast

Delta's own CHECK enforcement catches the bad row — validation is not our code guessing.

05 · Heal

Time-travel restore

RESTORE TABLE … TO VERSION AS OF — a metadata operation, not a data rewrite.

06 · Explain

Intent, locally

Surface the recorded intent to the operator so the next migration is corrected, not re-attempted blindly.

Track 1 · why Entire is essential

Checkpoint-driven, not checkpoint-logged.

The distinction is the whole product. Plenty of tools write a checkpoint as a side effect. Warden reads one to make the recovery useful.

  • Without the checkpoint — a revert, and an engineer reconstructing intent by hand.
  • With it — a recovery that states what was attempted and why, so the corrected migration is the next step.

The healing decision depends on the checkpoint. Remove Entire and the feature is gone, not degraded.

Noon Curveball · Track 1 privacy boundary

The assumption that broke

We had been writing the full checkpoint intent into migration_log — a Databricks table, outside Entire's local boundary. "More context in the log is better" became wrong.

Fix 01

context_completeness

Every row is labelled complete / redacted / unavailable, so partial context can never be mistaken for whole.

Fix 02

LocalOnlyText

Intent is wrapped so leaking it is a type error. Its str() returns a placeholder — a careless future call site gets a placeholder, not a leak.

Fix 03

error_summary()

Reviewing our own fix found the same leak through another door: Delta errors can embed row values. Exceptions now cross the boundary as a type name only.

Fix 03 wasn't in the brief. It came from asking where else the same shape of leak could occur — and it was already there.

Entire Checkpoints · the resume criterion

A fresh session really did resume from a checkpoint — this one.

The rubric asks whether a fresh session can pick the work up from a checkpoint. We didn't stage a demonstration of that. It is how the Curveball response was built, and the commit history shows it:

Best Use of Databricks · an honest accounting

What is load-bearing, and what isn't

Genuinely Databricks

  • Delta time-travel is the rollback. RESTORE TABLE … TO VERSION AS OF — metadata-only, which is why it scales to large tables.
  • Delta CHECK enforcement is the failure trigger. The constraint validates existing rows at ADD CONSTRAINT time — the migration fails there, not in our code.
  • Lakeview dashboard — a real workspace object over migration_log, built through the REST API.

Portable, and we'll say so

  • The connector and logging path would work against any SQL warehouse. We're not claiming otherwise.
  • Synthetic data only — 50 generated users on the reserved example.invalid domain; user 007 carries plan='legacy' so the failure is deterministic.

Where this is useful

Four situations this already fits

Highest leverage

Agent-authored migrations

An AI agent proposes a schema change. Warden is the guard rail: the agent's own recorded intent becomes the explanation when the migration fails — and the privacy boundary keeps that intent off the warehouse.

Data quality

Rolling a rule onto legacy data

Exactly the demo: a business rule meets rows that predate it. You want the offending rows named and the table intact, not a half-applied constraint.

Incident response

3am schema rollback

The engineer who picks up the page is not the one who wrote the migration. The recorded intent is the difference between a five-minute fix and an hour of archaeology.

Compliance

Auditable change history

migration_log records every attempt, its outcome, and how complete the context was — deliberately without the sensitive text itself.

Limits, stated plainly

What we did not build

  • One table, one migration, one validation path. A narrow vertical slice proven end-to-end, chosen over a broad one that doesn't run.
  • A multi-table scheduler exists — and is excluded. We prototyped it today and left it out because it wasn't live-verified before the deadline. It's on the handoff branch, and the docs say exactly why it isn't shipped.
  • RESTORE fails if VACUUM purged the target version. Production needs a retention policy that guarantees the rollback window survives.
  • Validation is a full-table scan, and the token is a long-lived PAT. Both need to change before this is a production tool.

Next

From one table to a migration control plane

  • Multi-table, dependency-aware parallelism — independent tables migrating concurrently under a worker bound; same-table work strictly ordered; a failure isolated to its own table.
  • Live progress instead of a terminal pass/fail — rows processed, replay lag, phase, warehouse spend. That's also what makes health alerts meaningful mid-flight.
  • An operator in the loop — inspect what validation caught, correct the offending rows, approve or hold a cutover. The checkpoint boundary is what makes exposing that safe.
  • The migrations that actually frighten people — changing a primary key, splitting one table into several, merging several into one. A blind revert is least acceptable exactly where it's most likely needed.

Verify any of this yourself: bash warden/demo.sh for the live loop, or bash warden/demo.sh --self-test with no credentials at all.
